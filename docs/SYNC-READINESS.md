# آمادگی همگام‌سازی — مرحله ۹

> هدف: تعریف قرارداد داده‌ی قابل‌انتقال و ادغام سه‌طرفه، **بدون شبکه، بدون تغییر قالب محلی و
> بدون کلید ذخیره‌سازی تازه**. هیچ مسیر اجرایی برنامه به این ماژول وصل نشده است.

## مسئله

داده‌ی برنامه امروز فقط «وضعیت فعلی» است: آرایه‌های حساب/سند/چک/وام/... در `localStorage`.
برای همگام‌سازی امن باید به سه سؤال پاسخ داشت:

1. **چه چیزی باید منتقل شود** و با چه شناسه‌ای پایدار بماند؟
2. وقتی دو دستگاه یک رکورد را متفاوت عوض کردند، **کدام برنده است** و کاربر چطور می‌فهمد؟
3. اگر یک طرف رکوردی را حذف کرد، **حذف چطور منتقل شود** بدون اینکه با ویرایش طرف دیگر بجنگد؟

## قرارداد سند (نسخه ۱)

```json
{
  "format": "hesabno-sync",
  "version": 1,
  "createdAt": "…",
  "meta": { … },
  "collections": {
    "accounts": { "order": ["2", "1"], "entities": { "2": { … }, "1": { … } } },
    "transactions": { … }
  },
  "deletions": { "checks": ["c-1"] }
}
```

* **شناسه‌ی پایدار**: `id` خود رکورد؛ اگر نداشت، شناسه‌ای از محتوای متعارف (`~hash`). شناسه‌ی
  مشتق‌شده فقط در سند است و هرگز در داده‌ی محلی نوشته نمی‌شود.
* **`order`**: ترتیب آرایه در برنامه حفظ می‌شود؛ رفت‌وبرگشت، ترتیب UI را عوض نمی‌کند.
* **`deletions`**: سنگ‌قبر (tombstone) برای انتقال حذف؛ سنگی که هم‌زمان با موجودیت باشد رد می‌شود.
* **متعارف‌سازی**: کلیدهای شیء بازگشتی مرتب می‌شوند؛ داده‌ی یکسان همیشه سند بایت‌به‌بایت یکسان
  می‌دهد (اثر انگشت ۶۴ بیتی فقط برچسب سریع است، نه مبنای تصمیم).
* **رد صریح**: شناسه‌ی تکراری (مثلاً `1` و `"1"`)، موجودیت غیرشیء، سند ناهماهنگ، نسخه‌ی ناشناخته.

## ادغام سه‌طرفه

بدون «نسخه‌ی پایه» نمی‌توان فهمید کدام طرف عوض شده است. قاعده‌ی تصمیم برای هر موجودیت:

| پایه | محلی | مقابل | نتیجه |
| --- | --- | --- | --- |
| A | A | A | بدون تغییر |
| A | B | A | B (فقط محلی عوض شده) |
| A | A | B | B (فقط مقابل عوض شده) |
| A | B | B | B (هر دو یک تغییر) |
| A | B | C | **تعارض** — گزارش می‌شود |
| A | حذف | A | حذف منتقل می‌شود |
| A | حذف | B | **تعارض** (`delete-edit`) — بی‌صدا ناپدید نمی‌شود |

سیاست پیش‌فرض `unresolved` است: **مقدار محلی نگه داشته می‌شود** و تعارض با نسخه‌ی پایه/محلی/مقابل
برگدانده می‌شود تا UI بتواند از کاربر بپرسد. `prefer-local` و `prefer-remote` هم موجودند، اما
تعارض همیشه گزارش می‌شود (حتی وقتی سیاست صریح است) تا هیچ تغییری بی‌صدا از دست نرود.

ادغام **idempotent** است: ادغام دوباره‌ی نتیجه با همان سمت مقابل، نتیجه را عوض نمی‌کند.

## محدودیت‌های صریح

1. **هیچ شبکه‌ای وجود ندارد.** این مرحله فقط قرارداد و الگوریتم است؛ لایه‌ی انتقال، احراز هویت،
   رمزنگاری در انتقال و ذخیره‌ی نسخه‌ی پایه کار مراحل بعد است.
2. **نسخه‌ی پایه ذخیره نمی‌شود.** برای ادغام واقعی، برنامه باید آخرین سندِ همگام‌شده را جایی نگه
   دارد. این کار **کلید تازه** می‌خواهد و طبق قرارداد، بدون تأیید انجام نشده است.
3. **شناسه‌ها فقط در سطح مجموعه یکتا فرض شده‌اند**؛ برخورد عدد/رشته (`1` و `"1"`) عمداً خطا
   می‌دهد، چون در داده‌ی واقعی ممکن است هر دو شکل دیده شود.
4. **تعارض در سطح کل موجودیت است، نه فیلد.** دو دستگاه که فیلدهای مختلف یک سند را عوض کنند
   تعارض می‌بینند، نه ادغام فیلدبه‌فیلد. این محافظه‌کارانه و امن است؛ ادغام فیلدی در آینده ممکن
   است ولی نیازمند قواعد صریح per-field است.
5. **زمان/ترتیب واقعی ویرایش در داده‌ی محلی نیست** (نه `updatedAt`، نه شماره‌ی نسخه). بنابراین
   «آخرین نوشته برنده» ممکن نیست و همان ادغام محتوایی بالا استفاده می‌شود.
6. عددهای میزسنج روی Node و همین ماشین‌اند؛ ادغام ۵۰k روی WebView کندتر است و برای همین در
   پس‌زمینه/با فاصله اجرا می‌شود، نه در مسیر کلیک کاربر.
