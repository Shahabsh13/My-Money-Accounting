# کیبورد مبلغ — رفتار پیش‌نویس و بلور پس‌زمینه

> دامنه: فقط `214-hesabno-numeric-keyboard.js` (+ بامپ نسخه در `index.html`). فایل ۲۲۵ (رنگ‌بندی)
> دست نخورد. هیچ کلید ذخیره‌سازی، قالب داده یا قاعده‌ی حسابداری عوض نشد.

## ۱) قبل از تغییر

هر رقم مستقیم در فیلد نوشته می‌شد و رویداد `input` منتشر می‌شد:

```
لمس فیلد → activateInput → هر رقم → setAmount() → activeInput.value = digits + input event
```

یعنی تا قبل از زدن «تأیید» هم مقدار در فرم/react state نشسته بود. بستن با × مقدار نیمه‌کاره را
باقی می‌گذاشت. صفحه‌ی زیر کیبورد هم بدون هیچ جداسازی بصری دیده می‌شد.

## ۲) بعد از تغییر

```
لمس فیلد → activateInput → draft = مقدار فعلی فیلد → نمایش draft در نمایشگر کیبورد
هر رقم       → فقط draft عوض می‌شود (بدون لمس فیلد، بدون رویداد)
«تأیید»      → commitDraft(): یک‌بار value + یک‌بار input + یک‌بار change → بستن
×  یا Esc    → draft دور ریخته می‌شود؛ فیلد همان مقدار قبلی می‌ماند
```

* **پیش‌نویس با مقدار فعلی فیلد شروع می‌شود** (مثلاً ۱۲۰۰ → «۱٬۲۰۰» → backspace → «۱۲۰»).
* ورودی فیزیکی (`keydown`) هم روی draft کار می‌کند و `Enter` تأیید است.
* اگر مقدار فیلد از بیرون عوض شود، پیش‌نویس هم‌گام می‌شود (بدون نوشتن معکوس).
* `MAX_DIGITS = 15`، حذف صفرهای ابتدایی و رد مقدار منفی مثل قبل.

## ۳) بلور پس‌زمینه

یک `<div id="hesabno-amount-keyboard-backdrop">` **فقط در اولین بازشدن** ساخته می‌شود
(پس DOM بوت دست‌نخورده می‌ماند) و با `hidden` روشن/خاموش می‌شود:

```css
position: fixed; inset: 0; z-index: 2147482999;   /* یک لایه زیر کیبورد */
background: rgba(2,6,23,.24);
backdrop-filter: blur(2px) saturate(.96);          /* «کمی تار» */
```

چرا `backdrop-filter` و نه `filter` روی `#root`؟ چون `filter` روی والد، containing block فرزندان
`position: fixed` (نوار پایین، مودال‌ها) را می‌شکند و می‌تواند چیدمان را جابه‌جا کند. این لایه فقط
روی تصویر پشتش اثر می‌گذارد. تم روشن رنگ پرده‌ی روشن‌تر دارد. با
`prefers-reduced-motion` انیمیشن ورود حذف می‌شود. در WebViewهای قدیمی که `backdrop-filter`
ندارند، فقط سایه‌ی رنگی می‌ماند (تخریب تدریجی، بدون خطا).

## ۶) باگ «روی گوشی رقم ثبت نمی‌شد» (اصلاح‌شده)

همه‌ی کارها در هندلر `click` بود، در حالی که همان دکمه‌ها روی `touchstart`/`pointerdown`
`preventDefault()` می‌زنند. در کرومِ لمسی و WebView اندروید، لغو `touchstart` رویداد مصنوعی
`click` را **تولید نمی‌کند**؛ بنابراین روی گوشی هیچ رقمی ثبت نمی‌شد، ولی با ماوس در دسکتاپ
کار می‌کرد (و آزمون‌های قبلی که `.click()` صدا می‌زدند هم سبز می‌ماندند — همان نقطه‌ی کور).

اصلاح: خودِ «فشردن» کار را انجام می‌دهد:

| محیط | رویداد عمل | چرا |
| --- | --- | --- |
| همه‌ی مرورگرها | `pointerdown` | پاسخ فوری، مستقل از click |
| WebView قدیمی (بدون `PointerEvent`) | `touchstart` + `mousedown` | مسیر جایگزین |
| صفحه‌کلید/فناوری کمکی | `click` با `detail === 0` | فعال‌سازی واقعی صفحه‌کلید |

جلوگیری از دوبار اعمال: `click` مصنوعی که روی همان دکمه و کمتر از ۸۰۰ms بعد می‌آید نادیده
گرفته می‌شود (ضربه‌های سریع پشت‌سرهم همچنان هر کدام یک رقم‌اند، چون هر کدام `pointerdown` جدا دارند).
چون `preventDefault` حالت `:active` را می‌کشد، بازخورد فشردن با کلاس `hkap-pressed`
(مقیاس ۰٫۹۶ + روشنایی) جبران شده است.

آزمون‌های تازه: فشردن اشاره‌گر بدون click، عدم اعمال دوباره در click مصنوعی، و مسیر
`touchstart` در WebView قدیمی → `tests/ui-keyboard-regression` **۱۳/۱۳**، کل **۲۰۲/۲۰۲**.

## ۷) بازگشت

تغییر یک‌فایلی است: `git revert` کامیت این مرحله کافی است. اگر فقط بلور لازم نیست، می‌توان
`backdrop.hidden = false` را برداشت یا `#…-backdrop` را با `display:none` خنثی کرد.

## ۸) محدودیت‌ها

1. **اثبات پیکسلی نداریم.** jsdom چیدمان و `backdrop-filter` را نقاشی نمی‌کند؛ ادعای «ظاهر دقیقاً
   همان است» فقط برای ساختار DOM و متن است، نه تصویر.
2. اگر کاربر وسط تایپ، فیلد را با لمسی دیگر عوض کند، پیش‌نویس دور می‌شود (رفتار قبلی هم همین
   بود که مقدار نیمه‌کاره می‌ماند؛ حالا دور ریخته می‌شود).
3. **مرورگر واقعی در محیط توسعه نیست.** مسیر لمسی با شبیه‌سازی jsdom آزموده شده است
   (`PointerEvent` ساختگی و مسیر `touchstart`)، نه روی گوشی. ادعای «روی گوشی درست شد» بر پایه‌ی
   مدل رویداد استاندارد است، نه مشاهده‌ی مستقیم.
4. `apply()` هنگام `input` خارجی با مقدار متفاوت، پیش‌نویس را بازنویسی می‌کند — عمدی است تا
   نمایشگر هرگز مقدار کهنه نشان ندهد.
