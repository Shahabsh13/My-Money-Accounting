# ممیزی شروع مهاجرت کامل به Kotlin Native

## هدف نهایی

- رابط کاربری Native با Kotlin و Jetpack Compose، با حفظ ظاهر فعلی فارسی/RTL تا حد امکان.
- منطق مالی مستقل از UI و قابل‌آزمون در Kotlin.
- ذخیره‌سازی محلی Native (Room برای داده‌های ساختاریافته، DataStore برای ترجیحات، فایل‌سیستم برای پیوست‌ها/خروجی‌ها).
- بدون سرور اجباری؛ همگام‌سازی ابری موضوع جدا و اختیاری است.
- WebView فقط در دورهٔ مهاجرت به‌عنوان مسیر مقایسه/بازگشت باقی می‌ماند و پس از برابری کامل حذف می‌شود.

## وضعیت فعلیِ بررسی‌شده

نقشهٔ اولیهٔ صفحه‌ها، قابلیت‌های Android، کلیدهای داده، پشتیبان و قرارداد تاریخ در `docs/native-migration-map.md` ثبت شده است. این نقشه عمداً «اولیه» علامت‌گذاری شده، چون UI اصلی فشرده است و باید در ادامه با آزمون/استخراج بیشتر کامل شود.

- ماژول Android فعلی یک `app` است؛ `app/build.gradle` از Android Gradle Plugin 8.9.2، Java 17، `minSdk 24` و `targetSdk 35` استفاده می‌کند.
- `MainActivity.java` از `ComponentActivity` ارث می‌برد، WebView را با `WebViewAssetLoader` اجرا می‌کند و از پل JavaScript به نام `HnBridge` برای Back، ذخیرهٔ پشتیبان، مجوزها و قابلیت‌های Android استفاده می‌کند.
- UI در `app/src/main/assets/index.html` و بسته‌های JavaScript/CSS اجرا می‌شود. هستهٔ رابط در `src/scripts/067-inline.js` (حدود 4.66 MB) یک باندل فشرده است؛ سورس مستقل React/کامپوننت‌ها، اسکریپت build وب و source map در مخزن پیدا نشد. این مورد پیش از بازسازی UI باید تعیین تکلیف شود: سورس اصلی بازیابی شود یا باندل به‌صورت کنترل‌شده به اجزای قابل‌ممیزی تفکیک گردد.
- چند ماژول دامنهٔ JavaScript مستقل در `src/domain/` وجود دارد (حساب‌ها، دفترکل، اعداد، گزارش‌ها، پشتیبان و همگام‌سازی) و رجیستری کلیدهای ذخیره‌سازی در `src/storage/keys.js` است.
- دادهٔ اصلی WebView از `localStorage` و نگهبان ذخیره‌سازی عبور می‌کند. Android نیز SQLite/فایل‌سیستم بومی برای key-value، پیوست‌ها و نسخه‌های پشتیبان دارد؛ بنابراین داده و پیوست‌ها از ابتدا در یک محل واحد نیستند.
- قالب پشتیبان فعلی در دامنه نسخهٔ 5.1 است و قرارداد کلیدهای فعلی/قدیمی آزمون دارد؛ هر مهاجرت باید همین داده‌ها را بخواند و قابل‌بازیابی نگه دارد.
- Kotlin 2.2.0 و Compose به Gradle افزوده شده‌اند. یک `NativeMigrationPreviewActivity` آزمایشی فقط در source set مربوط به debug قرار دارد؛ Activity اصلی و launcher تولیدی همچنان `MainActivity`/WebView است. هیچ مسیر کاربری یا داده‌ای به این نمونه متصل نشده است.
- `app/src/main/java/com/maymoney/app/domain/JalaliDate.kt` منطق خالص تاریخ شمسی را دارد: parse/format، طول ماه/کبیسه، جمع ماه و تبدیل weekday مطابق قرارداد فعلی. `JalaliDatePickerSheet` و قواعدش در Compose افزوده شده‌اند؛ فقط preview debug آن‌ها را نشان می‌دهد و هیچ داده یا مسیر production را نمی‌خواند/نمی‌نویسد. برابری بصری روی دستگاه هنوز بررسی نشده است.
- این محیط JDK و Android SDK ندارد، بنابراین build محلی Android قابل‌اجرا نیست؛ با این حال build و آزمون‌های Android در GitHub Actions برای SHA نهایی این مرحله موفق شدند (جزئیات در بخش اعتبارسنجی). نمونهٔ Compose هنوز debug-only است و روی دستگاه از نظر ظاهری/insets/Back باید جداگانه بازبینی شود.
- در زمان این ممیزی، شاخهٔ جلسه فعال است اما درخت کاری شامل تغییرات ثبت‌نشده و فایل‌های تازه است. آن‌ها نباید با reset/checkout یا پاک‌سازی ناخواسته از بین بروند. ZIP سورس فعلی که قبلاً تهیه شد همین وضعیت را نگه می‌دارد.

## ترتیب اجرا و دروازه‌های عبور

1. **تکمیل ممیزی سورس و داده:** موجودی همهٔ صفحه‌ها، پل‌های Native، کلیدهای ذخیره‌سازی، پیوست‌ها، مجوزها و مسیرهای پشتیبان؛ تأیید اینکه آیا سورس اصلی UI وجود دارد یا نه.
2. **ثبت قرارداد رفتار و داده:** نمونه‌های طلایی دفترکل/مانده، قالب دقیق تاریخ شمسی، نسخه‌بندی مدل‌ها و معیارهای حفظ ظاهر فعلی.
3. **موفق:** پیکربندی Kotlin/Compose به‌شکل additive در CI کامپایل شد؛ آزمون‌های JVM و build debug نیز برای SHA ثبت‌شده موفق‌اند. launcher/path اصلی تغییر نکرده است.
4. **در انتظار آزمون دستگاه:** یک پوستهٔ Compose فقط در debug وجود دارد؛ RTL، رنگ‌های تیره و lifecycle آن روی emulator/دستگاه و insets/Back هنوز باید بصری بررسی شوند. نمونهٔ واقعی تقویم/تاریخ پس از ممیزی رفتارش می‌آید.
5. **دامنه و ذخیره‌سازی:** انتقال منطق به Kotlin و طراحی Room/DataStore فقط پس از تثبیت قراردادهای مالی و آزمایش مهاجرت یک‌باره از دادهٔ WebView.
6. **انتقال صفحه‌ها به‌ترتیب وابستگی:** هر صفحه پشت feature flag/مسیر آزمایشی و با آزمون برابری مستقل؛ نسخهٔ WebView تا پایان بازگشت‌پذیر بماند.
7. **تطبیق داده و انتشار آزمایشی:** بازیابی، شمارش و مانده‌ها باید با مبدأ برابر باشند؛ سپس آزمون دستگاه و CI.
8. **حذف WebView در آخر:** فقط وقتی همهٔ قابلیت‌ها، مهاجرت داده و مسیر rollback تأیید شدند.

## موارد ممنوع در این مهاجرت

- بازنویسی یک‌باره یا حذف WebView پیش از برابری رفتار.
- تغییر قواعد حسابداری صرفاً برای ساده‌کردن مدل Room.
- حذف/Skip آزمون‌های موجود.
- حذف دادهٔ قدیمی پیش از تأیید مهاجرت و قابلیت بازیابی.
- ادعای موفقیت build Android بدون اجرای آن در JDK/Android SDK واقعی یا CI.
